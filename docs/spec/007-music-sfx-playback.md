## 2. 設計總覽

```text
遊戲 ──呼叫──> 192B:0010 開始 / 0061 停止 / 00A0 淡出 / 011F 音效     聲音旗標 3E24:01B8 維持 0，函式本體照原樣空轉返回
          └──> 192B:0274 查詢 ─ 192B:02C9 讀狀態字
                     │ 指令剛執行完時，runtime 觀察
                     ▼
              runtime.SoundSink（介面）  MusicStart(mid) MusicStop() MusicFade(n) SFX(id,start,end) Playing() bool
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
   sound.Engine（玩家）       sound.NullSink（機器人、測試）
   合成、混音；命令佇列加      不出聲；Playing 的時鐘是遊戲 tick
   原子狀態字，無鎖
          ▲
          └── 唯一的拉取者：音訊裝置，或裝置不可用時的牆鐘拉取執行緒
```

- 遊戲環境不注入 `SOUND`、不載入驅動，旗標維持 0。沒有模擬硬體，也不需要 `CTMIDI.DRV`（`docs/re/010` 選項 A 與 D）。
- 掛鉤不取代函式本體。唯一對遊戲狀態的影響：(1) 狀態讀取指令之後修改 AX；(2) 停止常式的觀察點補寫 `2BCC:0223 ＝ 0FFh`（第 3 節）。**掛鉤不寫 `3E24:01BA`**，遊戲記憶體裡的聲音狀態字永遠是 0，所以診斷、機器人檢查點存下的狀態檔不帶聲音狀態，無 Sink 的工具載入它們不會卡在 `PlayMusic` 的等待迴圈（審查 A1、B5）。

## 3. 觀察點與動作（`apps/hr/runtime/sound.go`）

觀察時機是「指令剛執行完」（`Machine.Insn()` 回傳的起點，在 `Step` 開頭的 tick 之後才記下），不是「即將執行」。`Step` 開頭的 tick 可能先插入中斷處理，同一個位址會被「即將執行」的檢查看到兩次；`Insn` 每次呼叫恰好看到一次（審查 A R4、B S6）。四個進入點的第一道指令都是 `push bp`（`55`），執行完後 `SP` 比進入當下少 2，第一個引數在 `SS:SP+6`。

| 位址 | 剛執行完的指令 | 動作 |
|---|---|---|
| `192B:0010` 開始 | `push bp` | 從 `[3E24:01CE]:[3E24:01CC]` 起複製 `MidWindow ＝ 0x4E20` bytes（遊戲 `fread` 的上限，`docs/re/010` 第 2.1 節），呼叫 `Sink.MusicStart(複本)` |
| `192B:0061` 停止 | `push bp` | 寫 `2BCC:0223 ＝ 0FFh`，呼叫 `Sink.MusicStop()` |
| `192B:00A0` 淡出 | `push bp` | 讀 `SS:SP+6` 的低位元組為係數 `n`，呼叫 `Sink.MusicFade(n)` |
| `192B:011F` 音效 | `push bp` | 讀 `SS:SP+6` 的 16 位元為 `id`；`0x32 ≤ id ≤ 0x3B` 時讀執行期 `3E24:0008` 的切片表（每次呼叫都讀）取 `start`、`end`，`end > start` 時呼叫 `Sink.SFX(id, start, end)`；否則計入 `BadSFX` 並忽略 |
| `192B:02C9` 狀態讀取 | `mov ax,[3E24:01BA]` | 把 AX 的 bit 0 換成 `Sink.Playing()`（其餘位元不動）。接著 `and ax,1` 與 `retf`，`192B:0274` 的回傳值就是 `Sink.Playing()`。`192B:02C9` 是唯一讀 `3E24:01BA` 的指令（審查 A C4，confirmed）；`0274` 的所有路徑都經過它（`q1.out`） |

- 其他位址不動作。每步的額外成本：`Options.Sound` 為空時一次與 nil 的比較；非空時一次 `Insn()` 取值與段比較，段是 `192B` 才進入 `post`。
- **開啟時的位元組檢查**（失敗即關閉）：`Session.Open` 在 `Options.Sound` 非空時比對 10 個位置的位元組：上表的 5 個位址，加上設計依賴但不掛鉤的 `192B:0274`、`192B:059B`、`192B:0511`、`1043:21F8`（`PlayMusic`）、`1043:223C`（重播節拍）。位元組見 `apps/hr/runtime/sound.go` 的 `soundSites`，取自冷啟動記憶體並與反組譯一致（`docs/re/018` 第 4 節）。任何一處不符，`Open` 回傳點名該位址的錯誤。
- **旗標防護**：每次觀察前讀 `3E24:01B8`；不為 0（有人注入了驅動環境，函式本體會碰硬體）就永久停用掛鉤並記一行，之後不做任何動作，避免半套行為。
- **`MidWindow` 與有效長度**（B3、A2）：遊戲的 MID 緩衝在短檔之後殘留前一首較長曲子的位元組（`fread` 只寫檔案長度）。runtime 一律交出 `0x4E20` bytes 的複本（複本讓接收端不受之後 `059B` 覆寫緩衝影響，淡出期間舊曲不會變成新曲的位元組）。有效長度由接收端依 SMF 結構決定：`MThd` 的 8 加長度欄，加上宣告軌數個 `MTrk` 的（8 加長度欄），其後忽略（`sound.Song.Size`）。超過複本長度或截斷視為解析失敗。
- **`MusicStop` 的語意**（審查 B S9、A R8）：旗標為 0 時 `192B:0061` 本體會跳過清曲號的那一行。有驅動時（旗標不為 0）原版的停止常式會把 `2BCC:0223` 清為 `0FFh`。觀察點補寫這個值，讓行為與有驅動時一致。已知呼叫者：`0511`（先停止，再把曲號還原，不受影響）、`7B3A:0636`（停止後接 `059B(4)`，`059B` 會重設曲號）、`76B6:055F`（結束路徑）。這依呼叫者清單成立（`docs/re/010` 第 2.2 節，強推論）。

## 4. 語意

1. `Sink.Playing()`：已開始且尚未自然結束，也不在被停止或淡出的狀態。`MusicFade`、`MusicStop` 呼叫之後立即為假（`PlayMusic` 的 `0274` 迴圈不可阻塞）；`MusicStart` 之後立即為真。排隊中的曲子（淡出中收到的新曲）算播放中。自然結束是**最後一個事件的時間**（end-of-track 的最大 tick），不含釋放尾音。
2. **閒置時的 `MusicFade` 是空操作**（審查 A R1、重審 Z1）：開機的 `PlayMusic(16)` 與每次循環重播都先走 `00A0`，若閒置時也進入淡出狀態，新曲會被排在不存在的淡出之後。**閒置的定義：沒有目前曲，或目前曲已到曲末（自然結束，尾音仍在唱）。** 目前曲已到曲末時，`MusicFade` 只讓尾音自己唱完（不淡出、不排隊），新曲立刻開始。原因：遊戲的重播節拍在曲末後下一個 tick（最多約 55 毫秒）內呼叫 `PlayMusic`，而 27 個檔中 25 個的尾音長於 0.12 秒；若把尾音當成還在播，每次循環都會先淡出約 0.71 秒才開始新曲，原版沒有這個空檔（`0274` 在 bit 0 為 0 時提早離開）。`MusicFade` 時引擎已在淡出中則忽略；排隊中的曲子在 `MusicFade` 與 `MusicStop` 時被丟棄（否則 `0274` 迴圈要空轉到佇列曲播完，無拉取者時永遠）。`0511` 與 `7B3A` 的路徑是 `MusicStop` 接 `MusicStart`，沒有前導 `MusicFade`，立即生效。
3. 淡出中收到 `MusicStart`：新曲排到淡出結束才開始（最多一首排隊，後到者取代）。遊戲不阻塞：`Playing()` 在 `MusicFade` 後即為假，`PlayMusic` 馬上讀新曲並呼叫開始。
4. 淡出長度：`13 × ceil(2n/3) ÷ 18.2065` 秒（`sound.FadeSeconds`），`n ＝ 1` 時約 0.71 秒。依據：原版（有驅動、旗標為 1）淡出每級把混音器音量降 `0x11`，從 `0xDD` 起共 13 級，每級等計時器 `0Eh` 歸零，`0Eh` 設為 `2n`；遊戲的 INT 1Ch 處理常式（`1F8A:00CB`，位元組見審查 A R2：`FA 60 1E 06 BB AB 00 B9 10 00 2E 8B 07 0B C0 74 0A 48 74 04 48 74 01 48 …`）每個 tick 對每個非 0 計時器減 3（夾到 0），所以每級 `ceil(2n/3)` 個 tick。等級：強推論（真機的 INT 1Ch 頻率沒有驗證，這裡用名目 18.2065 Hz）。曲線：原版是 13 級階梯，本實作用線性斜坡，聽感差異未評估。
5. 音效：單一聲部，新的 `SFX` 取代尚未播完的舊音效（原版只有一組 DMA，`docs/re/018` 第 3 節第 9 點）。切片取 `[start, end)`，來自觀察點讀的執行期表。取樣 8 位元無號、8000 Hz，線性內插升到 44100 Hz。PCM 資料由前端讀 `SOUND_E.PCM` 檔案交給引擎（`Engine.SetPCM`）：遊戲在旗標為 0 時不載入 PCM，客體的 `D000:8000` 一直是零（審查 A C7，confirmed）。原版多播 1 個樣本，本實作不重現（第 9 節）。範圍外的 `id` 在原版會讀到字串資料當切片表（審查 A C10），本實作忽略並計數。
6. SMF 解析：見第 5 節。**力度 0 的 note-on 視為 note-off**（原曲的音符都這樣結束）。同通道同音高重疊時，note-off 釋放最早的一個聲部。解析失敗（沒有 `MThd`、軌數為 0、事件截斷、SMPTE division、格式 2）時，`MusicStart` 忽略並回報，`Playing()` 維持原值。解析失敗的後果：`Playing()` 為假，遊戲的重播節拍每次都走 `PlayMusic`，退回現況每約 13K 道指令一次 `fopen`／`fread` 的 I/O（`docs/re/010` 第 4.2 節）；日誌必須限速（沿用 `ratelimit`）。原版檔案齊全時不會發生（27 個檔全部解析成功，`docs/re/018` 第 1 節）。
7. `Options.Sound` 為空時，遊戲行為與沒有這個功能時完全相同，包含重複讀 MID。非空時，遊戲可見的差異只有：(1) `192B:0274` 的回傳值；(2) `PlayMusic` 因此不再重複讀檔；(3) 停止常式之後 `2BCC:0223 ＝ 0FFh`；(4) 其後的指令軌跡（因為 (1)(2)），所以**有 Sink 的執行不能與既有收據逐步比對**（`docs/re/008` 收據 A、B、`docs/spec/003` 第 8 節的雜湊都是無 Sink 的）。同狀態 A/B 要在「Sink 的 `Playing()` 恆為假且路徑上沒有停止呼叫」的條件下才逐位元相同（第 8 節）。

## 5. 合成、時鐘與前端

### 5.1 引擎（`apps/hr/sound`）

| 項目 | 規格 |
|---|---|
| 輸出 | 立體聲 16 位元小端，44100 Hz。單聲部內容以相同音量送兩聲道（原曲沒有聲像資料，`docs/re/018` 第 1 節第 3 點） |
| SMF | 格式 0 或 1，division 為每四分音符 ticks；合併所有軌，相同 tick 時順序為 note-off、速度／音色／音量、note-on、軌結束；速度事件依序生效；支援 running status；其餘 meta 與 sysex 略過。事件只處理音符、program change、控制器 7（原曲只有這些，`docs/re/018` 第 1 節）。通道 10 當打擊樂。同一軌可以換音色、使用多個通道（`docs/re/018` 補記：`MAP3_1` 的 FM3 軌同軌 13 次 program change；`FM1` 軌使用通道 2 與 11） |
| 合成 | 雙運算元 FM（調變器與載波各一個波形與 ADSR、調變器回授、顫音）。音色參數表是本專案自行設計，見第 10 節。原曲 22 個 program 各有一組，其餘依 General MIDI 的 8 個家族預設。打擊樂 36、38、45、46、49 各一組合成，其他音符號用相近者 |
| 複音 | 上限 24 聲部；超過時取代最安靜的釋放中聲部，其次最早的聲部，並計入 `Steals`（原曲驗收要求為 0） |
| 音量 | 控制器 7 取平方曲線（`(v/127)²`，General MIDI 慣例），預設 100；力度曲線 `0.35 + 0.65 × v/127`；主增益固定為 0.30；限幅用 tanh 的有理近似。這些值**在驗收之前固定**，驗收只記錄各檔峰值，不用峰值反推增益 |
| 確定性 | 同一個 `GOARCH` 與建置下，相同 MID 得到逐位元相同的輸出（不使用隨機數或牆上時鐘；打擊樂雜訊用固定種子的線性同餘產生器）。跨 `GOARCH` 不保證（arm64 會融合乘加） |
| 執行緒 | `MusicStart`、`MusicStop`、`MusicFade`、`SFX`、`Playing` 由模擬執行緒呼叫（同一時間一個呼叫者），`Read` 由唯一的拉取者呼叫（拉取者的唯一性由前端的 `pullSource` 保證，見 5.2）。兩邊只透過一個有界命令佇列（64 個）與一個原子狀態字溝通，沒有鎖。狀態字是「世代 << 1 ｜ 播放中」：`MusicStart`、`MusicStop`、`MusicFade` 每個命令遞增世代並立即寫入（`SFX` 不遞增，否則音效會讓自然結束的 CAS 失敗，遊戲不再重播），音訊端偵測到自然結束時用 CAS 清除，世代已變就失敗，不會把較新的曲子的狀態清掉。`MusicStart` 的解析與建立渲染器在模擬端完成，`Read` 不配置記憶體（`testing.AllocsPerRun` 驗證）。佇列滿（拉取者停滯）時丟棄命令並記一行；被丟棄的是 `MusicStart` 時，狀態字同時改回「未播放」，否則沒有人會把它結束，遊戲永遠不重播 |
| `NullSink` | 不出聲、確定性：`Playing()` 的時鐘是客體的 tick 數（`machine.Ticks`），曲長 `ceil(秒 × 18.2065)` tick。給機器人、長跑與測試用，讓它們走和玩家相同的遊戲路徑而指令軌跡可重現 |

### 5.2 時鐘與拉取者（審查 B2、A R3、重審 S1）

「正在播放」的時鐘是拉取者的取樣時鐘，所以拉取者必須以牆鐘速度持續呼叫 `Engine.Read`，不論裝置是否可用或是否靜音：

- 有裝置：裝置的回呼（oto）或裝置執行緒（ALSA）就是拉取者。
- 裝置不可用、中途失敗或停滯：前端的牆鐘拉取執行緒（每 20 毫秒讀 882 個取樣框並丟棄）。
- 靜音（F3、`-mute`）：拉取者照常拉，`Engine` 輸出填 0。

這樣有裝置、無裝置、靜音三種情況的遊戲行為（重播時機）相同，只受牆鐘影響。不使用牆鐘的場合（機器人、長跑、測試）用 `NullSink`。

**拉取者的交接**：`Engine.Read` 不是並行安全的，所以所有拉取都經過前端的 `pullSource`，它用互斥鎖串行化，並用「世代」讓被接手的舊拉取者之後只拿到靜音、不再推進引擎。接手發生在兩種情況：裝置後端回報 `died`，或 `pullSource` 超過 `stallAfter`（2 秒）沒有成功拉取（例如裝置執行緒卡在阻塞的 `snd_pcm_writei`）。接手順序固定：先讓舊世代失效，再在背景關閉裝置（關閉可能阻塞，不能等），最後啟動牆鐘拉取執行緒。裝置的 `stop` 剛好被呼叫一次。程式結束時 `close` 最多等裝置關閉 1 秒。

### 5.3 音訊後端（審查 B1、重審 Z2）

- **不使用 `ebiten/v2/audio`**：它註冊的更新前掛鉤每幀檢查內部錯誤，裝置失敗時把錯誤當 `Update` 失敗回傳，`RunGame` 結束（審查 B1，讀 `ebiten/v2@v2.9.9/audio/audio.go` 與 `internal/ui/context.go`，強推論，未實跑；兄弟專案 `eob_123_remake` 在容器內踩過，必須帶 `-audio-cache ""`）。Docker、Xvfb、Wine 的驗收環境沒有音訊裝置，前端不可因此結束。
- **Linux**：`apps/hr/play/audio_linux.go` 用 `purego` 在執行期 `dlopen("libasound.so.2")`，呼叫 `snd_pcm_open("default", PLAYBACK)`、`snd_pcm_set_params`（`S16_LE`、interleaved、2 聲道、44100 Hz、軟體重取樣、延遲 100 毫秒）、`snd_pcm_writei`，欠載時 `snd_pcm_recover`。開不了庫、開不了裝置或寫入持續失敗，就退回牆鐘拉取執行緒。連結期沒有 ALSA 相依，AppImage 在沒有 `libasound` 的系統上照常啟動並靜音。Xvfb 容器內實測：載入了 `libasound.so.2`，`snd_pcm_open` 回報 `Unknown PCM default`，前端印出「音訊裝置不可用，靜音運行」並照常進入遊戲（`docs/re/019` 第 4 節）。
- **Windows、macOS**：`apps/hr/play/audio_other.go`（`//go:build !linux`）用 `oto/v3`：`NewContext` 回傳的 `ready` 通道等最多 3 秒，之後讀 `Context.Err()`；有錯誤或逾時就退回牆鐘拉取執行緒；執行中另有一個 goroutine 每秒檢查 `Err()`，出錯時通知接手（`Player` 由接手流程的 `stop` 關閉，先於牆鐘拉取執行緒啟動，不會有兩個並行的 `Read`）。**`Player.SetBufferSize` 設為 100 毫秒（17640 位元組）**：oto 的 `Player` 預設另有 0.5 秒的預讀緩衝（`oto/v3@v3.4.0/internal/mux/mux.go`，44100 × 2 × 2 ÷ 2 ＝ 88,200 位元組），不設的話點擊音會晚約 0.5 到 0.6 秒。
- **Windows 沒有音訊裝置時的行為不同**：oto 在兩個後端都找不到裝置時建立 `nullContext`，`Err()` 為 nil，不會出現「無音訊裝置，靜音」那行日誌，播放被丟進黑洞，拉取者仍在以音訊速度拉（因此「正在播放」的時鐘照常）。所以前端驗收的日誌判準分平台（第 8 節）。
- 延遲：Linux 裝置端 100 毫秒；Windows 與 macOS 設定 100 毫秒緩衝，預期點擊音延遲 0.1 到 0.2 秒，**沒有實測**（容器沒有裝置；第 9 節）。

### 5.4 前端行為

- F3 切換聲音開關（同時控制音樂與音效），預設開，寫入偏好設定（`docs/spec/006` 第 7 節的 `sound` 欄位）。F3 的選用理由：使用者指定 F1、F2、F4，聲音開關沒有指定鍵，F3 與它們相鄰；遊戲是否使用 F3 未普查（`docs/spec/006` 第 2 節的停止線同樣涵蓋 F3）。`Ctrl+D` 不用 F9 是因為診斷是低頻功能，聲音開關是高頻功能，兩者的取捨不同，不互相要求一致。
- 命令列 `-mute`，環境變數 `HR_MUTE`（`1` 或 `true`）。優先序：旗標、環境變數、偏好設定、預設（開）。靜音開始時仍建立拉取者。
- 前端開啟時把 `SOUND_E.PCM` 讀進記憶體交給引擎；檔案缺失或與 `required.tsv` 的大小不符時，音效關閉，音樂不受影響。
- 切換提示文字與 F1 說明（`docs/spec/006`）列出 F3 與目前聲音狀態。

## 6. 失敗模式

| 情境 | 行為 |
|---|---|
| 位元組檢查不符（版本不同） | `Session.Open` 回傳錯誤，點名不符的位址與實際位元組 |
| 聲音旗標 `3E24:01B8` 不為 0 | 永久停用掛鉤，日誌一行 |
| 沒有音訊裝置、`libasound` 缺失、oto 失敗 | 退回牆鐘拉取執行緒，日誌一行；遊戲不受影響，前端不結束 |
| MID 解析失敗 | 忽略該次 `MusicStart`，限速日誌；遊戲退回重複讀檔的現況（第 4 節第 6 點） |
| `SFX` 的 `id` 在 `0x32` 到 `0x3B` 之外，或切片表值使 `end ≤ start`、`end` 超出 PCM | 忽略並計數，不崩潰 |
| 命令佇列滿 | 丟棄命令並記一行（沒有拉取者的錯誤用法） |
| `SOUND_E.PCM` 缺失或大小不符 | 音效關閉 |
| 診斷或檢查點存下的狀態檔 | 不含聲音狀態（掛鉤不寫 `3E24:01BA`）；無 Sink 的工具載入後不會卡住（第 8 節測試） |
| 注入了錯誤的 Sink（`Playing()` 在淡出後仍為真） | 遊戲卡在 `PlayMusic` 的等待迴圈，診斷（`docs/spec/005`）T2 會報警（第 8 節正對照）。這是 `H3` 的同型情境，不是本功能的缺陷 |

## 9. 原版 oracle 與已知差異

沒有原版聲音錄音，也沒有 `CTMIDI.DRV`，所以不做「與原版聲音對拍」，只對拍遊戲端協議（進入點、參數、狀態讀取、開檔次數）。已知差異：

| 差異 | 說明 |
|---|---|
| 音色 | 合成器是本專案設計的 FM 參數，不是原版 `CTMIDI.DRV` 的音色；對原版的貼近程度：未知。證據只有弱指向：MID 的樂器名 meta 都是 `MPU`（`docs/re/018` 補記） |
| 淡出與換曲 | 原版換曲要等淡出完才讀新曲，期間遊戲忙等約 0.7 秒；本實作不阻塞遊戲，新曲排在淡出之後。淡出曲線：原版是 13 級階梯，本實作線性 |
| 指令軌跡 | 有 Sink 時 `PlayMusic` 不再重複讀檔，之後的指令軌跡與無 Sink 不同；既有收據（`docs/re/008` 收據 A、B、`docs/spec/003` 第 8 節）都是無 Sink 的，不可與有 Sink 的執行逐步比對 |
| 停止 | 旗標為 0 時原版的停止常式不清曲號；本實作補寫（與有驅動時一致） |
| 音效 | 原版多播 1 個樣本，切片 0 含檔頭 4 bytes；本實作取半開區間，切片 0 同樣含檔頭。混音：原版音效與音樂走各自的硬體，本實作軟體相加並限幅 |
| 延遲 | Linux 裝置端緩衝 100 毫秒；Windows 與 macOS 的 oto 設定 100 毫秒緩衝（`Player.SetBufferSize`，不設的話預設另有 0.5 秒預讀）。預期點擊音晚 0.1 到 0.2 秒，**沒有實測**（容器沒有裝置） |
| 音樂與遊戲時鐘脫鉤 | 拉取者用牆鐘，遊戲時間由 `Session` 的模擬速度決定。模擬跟得上牆鐘時兩者一致；慢機器上模擬落後，遊戲時間比牆鐘慢，音樂（牆鐘）會領先遊戲，曲末後遊戲的重播節拍依遊戲時間觸發，所以曲子結束到重播之間可能出現靜音空檔。不做追趕或同步 |
| macOS 音訊路徑 | 完全未驗證（沒有實機，交叉編譯環境也不能執行）；Windows 只驗證能編譯與 Wine 內前端不結束 |
| 無 Sink 的工具 | 診斷工具、`probe`、不帶 `-sound` 的機器人沒有 Sink，軌跡與玩家不同（遊戲重複讀 MID）；要走玩家路徑用 `hrbot -sound`（`NullSink`） |
| 重複讀檔 | 有 Sink 時消除（30M 步內 1706 次降為 1 次；`docs/re/017` 第 6 節的 2 遊戲小時長跑中 `NATIONAL.MID` 被開 263,768 次） |
| F3 | 新增保留鍵，原本送進遊戲；遊戲是否使用未知 |

## 10. 音色參數表的來源與記錄

`apps/hr/sound/patches.go` 的音色參數（頻率倍數、調變指數、回授、包絡時間、顫音）是本專案自行設計的數值，沒有使用也沒有複製任何現成音色庫、GENMIDI、SoundFont、驅動資料或晶片暫存器傾印。無法用測試證明這一點，所以用流程紀錄：

- 檔頭註明設計方法（依 General MIDI 音色名稱，以聲學直覺手調 FM 參數）、日期（2026-10-03）、處理者（AI 協助，未經人工審核）、「未參考任何音色庫、GENMIDI、SoundFont 或晶片暫存器傾印」；
- 每個 program 一組、有名稱（音色名是 General MIDI 的通用名稱，不是原版資料）；
- 數值用音樂量表達（倍率、秒、弧度），不用晶片暫存器位元組；
- 單元測試用的 MIDI 全是測試內組出的位元組，不是原曲轉錄。

## 11. 停止線與權利邊界

- 引擎與參數表是本專案自己的程式與數值，不含任何原版位元組。原版的 MID 與 PCM 只在執行期從玩家自備的原版目錄讀入。
- 離線轉出的 WAV、頻譜圖與波形截圖是原版音樂的衍生物，只放 `workplace/out/music/`，不提交，不進 `docs/images/`，不進發行包。發行包不含音訊檔，只含引擎（含 HD 的包同樣）。外洩掃描納入音訊（第 8 節）。
- `oto/v3` 是 Apache-2.0，通知文字進 `THIRD_PARTY_NOTICES.txt`（`tools/package.sh` 的 `make_notices`）；`purego` 原本已列。
- 停止線：位元組檢查不符；聲音旗標不為 0；遊戲被證實使用 F3；`SOUND_E.PCM` 的切片表與 `docs/re/018` 不符；需要把音訊檔放進發行包（先問使用者）；使用者試聽後認為音色不可接受（回到參數表，不是回到本規格）。
- 本規格不涵蓋：模擬 `CTMIDI.DRV` 的硬體路徑、播放原版沒用到的曲目、音量與音色的使用者設定畫面、`OP.EXE`／`END.EXE` 片頭片尾的音樂。要做這些先改規格。
- 在使用者試聽並接受之前，不寫「原版音樂已完整重現」。
